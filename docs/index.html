cc-relay

Claude Code on Web セッション間の調整レイヤ — stdio MCP + GitHub Issue ブローカー

概要 全体像 起動フロー 通知フロー プラン操作 認証フロー ロードマップ GitHub

概要

cc-relay は、複数の Claude Code on Web セッションが同じタスクに並行で取り組むときに、 セッション間で通知と共有プランをやり取りするための小さな stdio MCP サーバ (rust-mcp-agent) と、 その後ろにいる ブローカー の組み合わせです。

ブローカーは Broker トレイトでプラガブル。MVP の実装は GitHub Issue を使います — 専用 Issue の body に共有スナップショット (アクティブなエージェント一覧 + 共有プラン) を持ち、 comments をエージェント間メッセージのログとして使う構成。Web サンドボックスから個別インフラ無しに到達できる 唯一の汎用永続サービスだから、というのが選定理由 (詳しくは ARCHITECTURE.md の ADR-001)。

ステータス: WIP。今日 (2026-05-14) で P3 (ADR-001 採用) と P4 の Broker scaffolding まで着地。 実 GitHubBroker 実装は P4b 以降。

全体像

2 つの Claude Code on Web セッション (= それぞれ別 container) が、自分の中で動く stdio MCP サーバを介して 共有 GitHub Issue を読み書きする。直接の通信路は存在せず、すべて GitHub REST API 経由。

Session A と Session B は 互いの存在を直接知らない。GitHub Issue が状態の唯一の真実。 各セッションは自分の MCP サーバ越しに「最後に読んだ comment_id 以降」を polling して、自分宛のメッセージを inbox に書き出す。

セッション起動フロー 検証済 (2026-05-14)

Claude Code on Web がリポジトリを開いた瞬間に、自動で MCP サーバが立ち上がるまでの流れ。 2026-05-14 の probe で全往復を実測確認済み。

sequenceDiagram autonumber participant W as Claude Code on Web participant Repo as repo (default branch) participant Hook as SessionStart hook participant Bin as rust-mcp-agent W->>Repo: git checkout (default branch) W->>Hook: SessionStart event 発火 Hook->>Hook: Rust binary を準備
(GitHub Release から DL or cargo build) Hook-->>W: ok W->>Repo: .mcp.json を読む Repo-->>W: { "mcpServers": { "cc-relay": { "command": "rust-mcp-agent", "args": ["stdio"] } } } W->>Bin: spawn (stdin/stdout で MCP) Bin->>W: initialize → notifications/initialized → tools/list W-->>Bin: ready Note over W,Bin: 以降 mcp__cc-relay__notify_agent 等が使えるようになる

.mcp.json は session 起動時に 1 回だけ読まれる。途中で書き換えても効かない。 binary 更新時は session 再起動が必要 — これが SessionStart hook で binary を毎回最新化する設計理由。

通知フロー (notify_agent → 相手のプロンプトに到達)

エージェント A が「ねえ B、これお願い」を投げて、エージェント B が次にプロンプト書く直前にそれを目にするまで。 ブローカー (GitHub Issue comments) を経由した非同期 polling。

MA->>GH: POST /issues/N/comments
{type:"notify",to,from,msg,...} GH-->>MA: 201 + comment_id MA-->>CA: ok end rect rgb(31, 41, 55) Note over MB,Inb: 受信側 (定期 polling) MB->>GH: GET /comments?since=cursor (ETag) alt 変化なし GH-->>MB: 304 Not Modified else 新着あり GH-->>MB: 200 + [new comments] MB->>MB: filter (to == B ll to == "*")
+ exclude self-sent MB->>Inb: append 各 message (JSONL) MB->>MB: cursor を更新 end end rect rgb(31, 41, 55) Note over CB,Inb: 次のプロンプト直前 CB->>MB: get_inbox() MB->>Inb: read_all + rename → .read MB-->>CB: messages 配列 Note over CB: messages が Claude のコンテキストに入る end

押さえポイント:

  • 遅延は polling 間隔 + GitHub API RTT で支配される (数百ms オーダー)。WebSocket より遅いが「人間のループに乗る」用途なら十分。
  • ETag を使うので、誰も話してない時の rate limit 消費はほぼゼロ (304 が返るだけ)。
  • inbox の rename によって、同じメッセージが 2 回 Claude のコンテキストに入らないことを保証。

共有プラン操作フロー (ETag CAS)

共有プラン (タスクリスト) は Issue body に JSON snapshot として持つ。同時に複数エージェントが mutate する時の競合は ETag を使った CAS (Compare-And-Swap) で解決する。

sequenceDiagram autonumber participant A as agent-mcp participant GH as GitHub Issue body loop 最大 3 回 retry A->>GH: GET /issues/N GH-->>A: 200 + body(JSON) + ETag A->>A: PlanOp::Claim / Update / ... を snapshot に適用 A->>GH: PATCH /issues/N
If-Match: ETag
body: 新 snapshot alt 200 OK GH-->>A: ok + 新 ETag Note over A: cursor.last_etag を更新して return else 412 Precondition Failed GH-->>A: 競合 (他エージェントが先に更新) Note over A: snapshot 取り直して reapply end end Note over A: 3 回失敗 → BrokerError::Conflict { retries: 3 }

PlanOp の variants は Add / Claim / Update / Remove。 Claim はすでに他エージェント (live) に握られていれば失敗する。Done / Cancelled なタスクは再 Claim 可能。

認証フロー (GitHub App → installation token)

ブローカーが GitHub API を叩く認証は、専用の GitHub App cc-relay-agent の installation token を使う。 PAT より:

  • token は 1 時間で自動失効 (PAT 漏洩より傷が浅い)
  • rate limit が 5000 req/h/installation で広い
  • App 単位の audit log が残る
  • 将来 webhook で push 受信に切り替え可能

秘密鍵 (.pem): リポジトリには絶対に置かない。.gitignore で *.pem/*.key を弾いている。 管理は 1Password 等の secret store で。詳細は docs/github-app.md。
